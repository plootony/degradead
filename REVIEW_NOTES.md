# Review notes — test-fusion prototype

## What this is
Throwaway prototype validating one hypothesis: **Godot 4.7.2 + Photon Fusion (Godot SDK 3.0.0 *preview*, build 555) + Client-Server topology with prediction + Mixamo model + hitscan with server-side validation** holds together under real network latency. Not a game. Polish, IK, custom rigs, UI are explicitly out of scope per the original spec.

## Status
- Steps 1–3 (import, controller, animations) and Step 4a (networking + single-collider hitscan): **implemented and verified** by automated two-instance tests against live Photon Cloud.
- Step 4b (per-bone hitboxes + lag-compensated rewind): **implemented but switched off** — `NetConfig.HITBOX_MODE = "single"`. Flip to `"modular"` to exercise it. It has *not* been verified end to end.

## Fusion preview-SDK gotchas — these look like bugs but are deliberate
Every one of these was found empirically (the official docs are behind a bot-wall; the C# wrappers in `addons/fusion/cs/**` are the de-facto API reference). **Do not "simplify" these away.**

1. `input_authority` is **method-only** (`set_input_authority`/`get_input_authority`), not a registered property — `replicator.set("input_authority", …)` silently no-ops. `root_path`/`owner_mode`/`root_replication_mode` *are* real properties.
2. `FusionSpawner.spawn()`'s **pre-spawn Callable never fires**; the returned node is configured synchronously instead.
3. RPC targets must be **networked nodes** (carrying a replicator). Addressing the `MatchServer` autoload failed with `No FusionReplicator found for object 'Node'` even after `register_broadcast_receiver()`. Hence RPC endpoints live on `Player` and delegate to `MatchServer`.
4. RPC receivers still need Godot's standard **`@rpc` annotation**, despite Fusion using its own dispatch.
5. `root_replication_mode` must be `1` (Auto) or **nothing replicates** — remote peers see objects frozen at spawn.
6. `fusion/connection/mode` is **Cloud vs self-hosted Local**, *not* topology (setting it to 1 makes the client dial `127.0.0.1:5055`). Topology is `fusion/simulation/mode` (int; `1` = ClientServer, confirmed via `Fusion.get_simulation_mode()`).
7. `FusionServerReplicator` **must exist in the .tscn**, not be created in `_ready()` — the spawner scans the instantiated scene before `_ready()` runs and hard-crashes otherwise.
8. `on_process_input` **does not fire on non-master clients**; on the master it fires *synchronously inside* `queue_input()`. This drives the split in `_physics_process`: owner queues (and, if not master, drains for prediction); master drains for objects it doesn't own.
9. `Fusion.get_rpc_sender()` returned 0 in testing, so the shooter id is also passed explicitly and the server prefers its own value when available.
10. The Photon **App ID must be created with dashboard SDK "Version 3"** (Unreal/Godot). A Fusion-2 App ID fails room creation with `Unsupported Plugin` (32752) regardless of topology or region.

## Asset gotchas
- Godot's importer rewrites `mixamorig:Head` → `mixamorig_Head` (colon is illegal in node names).
- `Tony.fbx`'s own clip imports as `mixamo_com` and **is the T-pose** — must not be used as idle.
- `aks-74.fbx` is ~10× oversized (9.2 m); `_normalize_weapon_scale()` measures its AABB and rescales to 0.9 m. The file also contains loose props next to the rifle (a cartridge `54539`, its case, and a spare empty magazine) — `Player._strip_weapon_extras()` drops them by node name. Barrel is +X, up is +Y, grip around (-0.93, -1.0, 0) in rifle units; `WEAPON_IN_HAND_BASIS` / `WEAPON_PALM_OFFSET` map that into the Mixamo right-hand bone frame (+Y wrist→knuckles, +Z palm normal).
- Mixamo models face **+Z**; the visual container is rotated 180° so the character doesn't run backwards.

## Where to focus review
- **Artificial delay removed** (was 125 ms in `MatchServer.resolve_shot()` only). Shots resolve synchronously on the master; latency is whatever Photon gives you.
- **Lag compensation (4b)** uses sphere-vs-ray, rewinding by `Fusion.get_rtt()` (seconds, observed ~0.2 to the "us" region) clamped to `HITBOX_HISTORY_SEC`, and approximates every bone as a sphere. Level geometry occludes. Unverified end to end.
- **Health/death** is master-authoritative (`MatchServer._hp`); every peer mirrors hp from the broadcast hit report and plays `dying` locally. Respawn is a master timer → `Player.broadcast_respawn()` → `rpc_respawn` on all peers (sets position + `teleport()` on the replicator, best effort).
- **Animation clips are patched at merge time**: Mixamo exports have `loop_mode = NONE` (run cycles froze after 0.5 s). `Player._bake_in_place()` strips horizontal hips translation from EVERY merged clip now (not just loops) — a one-shot with baked-in hip travel (a turn, `Stand Up`, a jump) would otherwise drag the mesh away from the physics-driven capsule for the clip's duration too. Direction (forward/backward/left/right) uses a ±0.35 dead band with hysteresis so the choice doesn't flip every tick; forward pace (walk/run/sprint) is picked from *observed* speed (`_forward_pace_clip()`), not the sprint input flag, so it's correct for a peer that only ever sees replicated position.
- **Stance system (2026-09-08)**: `Stance.{STAND,CROUCH,PRONE}`, `C` toggles crouch, `Z` toggles prone (from either stand or crouch; toggling again always stands up via `Stand Up.fbx`, per the file the user added specifically for that). Broadcast via `rpc_set_stance` (same `call_local` pattern as `rpc_set_weapon_slot`). Known asset gaps, all deliberate fallbacks documented next to `LOCOMOTION_CLIPS`/`STANCE_TRANSITION_CLIP` in `player.gd`: no direct stand↔prone clip (snaps instantly, no `stand_to_crouch`-style transition); no mirrored crouch-strafe-right clip (falls back to the forward crouch-walk clip); no continuous prone backward/strafe loop (`Prone Backwards Stop`/`Prone Forward` reused, best effort — the "Stop" name suggests it may actually be a stop-transition, not a loop; wasn't previewable without the editor). `Getting Up.fbx` and `Left Turn.fbx`/`Strafe Right.fbx` were downloaded but are intentionally unused (no knockdown/stagger state exists to trigger the former; the latter two duplicate `Right Strafe`, see below).
- **Turn-in-place was added, then removed (2026-09-08)**: `Standing Turn 90 Left/Right.fbx` looked like turn animations by name but, on actually seeing them in play, turned out to be a look-around idle (head/torso swivel in place, not a body turn) — mouse-look was visibly making the character "look around" as if startled instead of pivoting to face the new direction. Deleted from the project entirely (`Standing Turn 90 *.fbx` and their `.import` files) along with the whole feature (`TURN_IN_PLACE_RATE`, `_prev_yaw`, the yaw-delta check in `_update_animation()`, the `turn_left_90`/`turn_right_90` clip-table entries and `ACTION_CLIPS` slots). The body just snaps `rotation.y` to the mouse yaw with no dedicated turn animation now, same as before this whole animation pass. A real turn-in-place would need a correctly-tagged clip (or decoupling body facing from camera yaw) — not attempted here.
- **`Crouch To Stand.fbx` was also the wrong animation, same day**: rather than download a replacement, `rpc_set_stance()` now plays `Stand To Crouch.fbx` backwards for the CROUCH -> STAND transition (`Player._play_action_reversed()`, `AnimationPlayer.play(name, -1.0, -1.0, true)`), so going down and standing back up are visually the exact same motion in reverse. `Crouch To Stand.fbx` and its `.import` were deleted; `crouch_to_stand_clip` no longer exists as a separate export. Both directions now also play at `CROUCH_TRANSITION_SPEED_SCALE` (1.6x) instead of the recorded 1x, which looked sluggish; `CROUCH_SPEED` (crouch-walk speed) was bumped 2.2 -> 3.0 the same pass.
- **`Hit Reaction.fbx` was also wrong (2026-09-08)**: it played a crouch, not a flinch, so a non-lethal hit visibly made the character sit down. Removed entirely (file + `.import` + clip-table entry) and replaced with a procedural flinch, `Player._play_hit_jerk()`: a small random rotation snapped onto the `Skeleton3D` node's own local `rotation` and eased back to zero via a `Tween` over `HIT_JERK_RECOVER_SEC`. Deliberately not an `AnimationPlayer` clip -- it rotates the skeleton *node*, which nothing else writes to (the `AnimationPlayer` only writes bone poses inside it, `SpinePitchModifier` too), so it layers on top of whatever locomotion/aim/fire animation is already playing instead of fighting with `_current_clip`/`ACTION_CLIPS`. Same technique would work for other "impact" beats (getting meleed, landing hard) if wanted later.
- **Jump/fall/land is inferred, not input-driven**: `_update_airborne_state()` reads vertical apparent velocity (`AIR_LAUNCH_THRESHOLD`) — same "read the body, not the input" approach as the pre-existing locomotion detection, so it works identically for the owner, a master-simulated remote, and a pure observer. The actual jump *impulse* is still input-driven (`jump` payload field, owner/master only, as it must be to affect physics).
- **Jump/Running Jump/Falling Idle/Landing/Hard Landing.fbx were all wrong, replaced entirely (2026-09-08)**: on top of the double-fire bug (a plain velocity threshold also reads the apex of the arc, where vertical speed crosses zero, as "landed"), the clips themselves turned out to be built for falling from a big height -- wrong content for this game's small hop, not just a mistuned threshold. Deleted the whole set (+ `.import` files) and replaced the discrete jump/fall/land clip state machine with a continuous procedural pose instead: `Player.LegTuckModifier` (a `SkeletonModifier3D`, same technique as `SpinePitchModifier`) bends the thigh and shin bones toward a "knees up" tuck, blended by `_leg_tuck_amount` (`move_toward`, `JUMP_TUCK_BLEND_SPEED`) toward 1 while vertical apparent speed exceeds `JUMP_TUCK_AIR_THRESHOLD` and back to 0 once it settles. This sidesteps the double-fire class of bug entirely -- there's no discrete state to mis-trigger, a momentary zero-crossing at the apex just pauses the blend for an instant instead of resetting anything. Layers on top of whatever locomotion clip is already playing (run/idle continue normally while airborne) rather than taking over the whole body like the old one-shot clips did. `_update_airborne_state()` and its constants (`AIR_LAUNCH_THRESHOLD`/`AIR_LAND_THRESHOLD`/`AIR_LAND_DEBOUNCE_SEC`/`HARD_LANDING_AIR_TIME`) are gone. **Bone rotation signs for the tuck are an unverified guess** (no editor in this environment to preview) -- if a leg bends the wrong way or looks stiff, flip the sign on `thigh_extra`/`shin_extra` in `LegTuckModifier._process_modification_with_delta()`.
- **Fire animation replaced the reload-as-fire hack**: `_play_fire_clip()` now plays `Firing Rifle.fbx` (`fire`/`crouch_fire`), `Reload.fbx` is unused by any trigger yet (no ammo/magazine system exists). Inherits the pre-existing gap where this only plays on the owner and the master (`_on_process_input` doesn't fire on other clients, gotcha #8 above) — a pure observer of a third player's shot won't see the fire pose, same as before, just now more visible since it's a real animation instead of the reload stand-in.
- **Melee (`F`, `Rifle Punch.fbx`) and weapon draw/holster (`Rifle Pull Out`/`Put Away.fbx`) are visual only** — melee deals no damage (no hit detection wired up), draw/holster plays alongside the existing instant re-parent in `_apply_weapon_slot()` rather than gating it.
- **Death variant is deterministic per peer, not sent over the wire**: `_die()` picks `death_headshot` for a `head` hitbox, else alternates `dying`/`death_alt` by `get_player_id() % 2` — every peer computes the same clip from data already in the broadcast hit report, no new RPC field needed. Non-lethal hits play `hit_reaction` once.
- **Proxy interpolation buffer temporarily removed** (`FusionServerReplicator.object_interpolation_time`, was `0.1` in `player.tscn`, taken out 2026-09-08 to test raw replication). For a peer that is neither owner nor master of a given `Player`, its position comes entirely from Fusion's `root_interpolation_mode` delivery -- that 100 ms buffer smoothed the gaps between snapshots. Put it back once raw (unbuffered) behaviour has been compared against it; see `Player._build_replicator()` for the matching TODO. `root_teleport_threshold = 2.5` (also newly added there, meters) stays either way -- it only matters for corrections bigger than any expected walking step, so it's not a source of the delay being tested here.
- **Camera rig**: one `CameraPivot → SpringArm3D → Camera3D` chain blended per frame between presets (`TPP_*`, `TPP_AIM_*`, `FPP_*` constants in `player.gd`). First person parks the pivot on a `BoneAttachment3D` at `mixamorig_Head` plus `FPP_EYE_OFFSET`, `near = 0.03`; the head mesh ends up behind the near plane so nothing is hidden.
- **Torso pitch** is a `SkeletonModifier3D` child of the skeleton (`Player.SpinePitchModifier`), NOT a `set_bone_pose_rotation` from `_process`: the latter accumulated every frame while the AnimationPlayer was paused (idle pose) and folded the character in half. Only peers that receive the player's input (owner + master) know `_pitch`; plain observers see a level torso.
- **Weapon slots** are broadcast via `rpc_set_weapon_slot` (call_local) and re-parent the same rifle node between the hand and `mixamorig_Spine2` attachments. Late joiners don't get the current slot (same limitation as the dead state).
- **Self-hit exclusion**: the third-person ray starts behind the shooter's head, so the shooter's own capsule is excluded from the query (previously that counted as a miss).
- `MatchServer.register_player()` is retried from `_on_process_input` because `input_authority` may not be set at `_ready()` time. Slightly hacky; worth confirming ordering guarantees.
- Test hooks `--automove`, `--autofire`, `--autoaim`, `--posdump`, `--room=` live in production code (opt-in via CLI args only). `--autoaim` faces the nearest other player so `--autofire` exercises hit → death → respawn.
- `Player._local_aabb()` composes local transforms manually — check the maths if the weapon scale ever looks off.
- `player.tscn` is intentionally a bare shell; almost the whole node tree is built at runtime in `_ready()` because the FBX import layout could not be inspected when it was written. Reasonable to revisit now that the editor is available.

## How to verify
The project is driven headlessly with a portable Godot build (no editor needed):

    godot --path . -- --autojoin --room=SOMECODE [--automove] [--autofire] [--posdump]

Run two instances with the same `--room` and diff their logs: `[POS ...]` lines should show both peers tracking both players, and `[shot]` lines should be identical on both sides. Use a fresh room code each run — Photon rooms outlive the process (`EmptyRoomTtlMs`) and a stale room makes the next run join as a non-master.

After deleting `.godot/`, regenerate it with `godot --headless --path . --import` — a plain run does **not** rebuild the import cache or register the GDExtension.
